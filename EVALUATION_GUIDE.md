# Human Evaluation Guide — Academic Feedback Summarisation

This document is written for anyone who wants to understand how the evaluation is designed, run a new evaluation on a different model or dataset, and interpret the results. No prior knowledge of the codebase is assumed.

---

## 1. Overview of the Evaluation Design

### What is being evaluated?

The pipeline takes a dataset of student feedback reviews and generates **text summaries** of that feedback organised along a **topic taxonomy tree** (e.g., "Approachability of Professor", "Quality of Lecture Slides"). Each summary condenses what students said about a particular topic. The human evaluation measures how good those summaries are.

### The topic taxonomy

The taxonomy is a fixed tree defined in `taxonomy_tree.txt`. It has five levels:

```
root  (Level 0)
└── Structure of Course  (Level 1)
    └── Workload  (Level 2)
        └── Deadlines  (Level 3/4 — leaf)
```

There are 82 nodes total: 58 leaves (where individual reviews are assigned) and 24 internal nodes (whose summaries are computed from child summaries bottom-up).

Two special kinds of nodes exist:
- **Regular leaf nodes** — standard topic categories.
- **Negative-sibling leaf nodes** — catch-all nodes whose names contain phrases like "nothing specifically", "but not", "in general not". These capture reviews that belong to a broad topic but not to any specific sub-topic.

### How are summaries generated?

Each node gets up to **four summary types** generated by an LLM (served via vLLM):

| Label | Type | Description |
|-------|------|-------------|
| **A** | Consolidated | Combines all feedback; has sections for Appraisals, Criticisms, and Suggestions |
| **B** | Positive-only | Only positive aspects |
| **C** | Negative-only | Only criticisms |
| **D** | Suggestion-only | Only suggestions for improvement |

For leaf nodes, the LLM's input is the raw annotated review tuples (aspect, opinion, sentiment). For internal nodes, the LLM's input is the child nodes' summaries (bottom-up propagation).

### How are evaluation records (samples) selected?

Each course partition yields a fixed set of records selected by `src/human_eval.py`:

| Selection | Count | Criterion |
|-----------|-------|-----------|
| Regular leaf nodes | 3 | Highest tuple count, but **< 20 tuples** total (to keep source material readable) |
| Negative-sibling leaf nodes | 1 | Highest tuple count, same < 20 filter |
| Internal node (Level 2–3) | 1 | Internal node with most tuples in that depth range |
| Internal node (Level 1) | 1 | Shallowest internal node with most tuples |
| Root node | 1 | Always included |

With 3 course partitions, this yields approximately **21 records** total across all courses.

### How are evaluators assigned to records?

- Each evaluator is assigned **7 records** (`N_RECORDS_PER_EVALUATOR` in `eval_app/config.py`).
- **3 of those 7 are "core" records** (`N_CORE_RECORDS`) assigned identically to every evaluator — these are used to compute inter-annotator agreement (IAA).
- Assignment is **deterministic**: the same evaluator name always produces the same assignment, so evaluators can log out and resume across multiple sittings.
- Assignments are persisted in `eval_results/registry_<dataset>_<model>.json`.

### How is the evaluation presented?

Evaluators access the app at `http://<server-ip>:8501`. After entering their name:

1. **Node info** is shown (topic path, type, level).
2. **Consolidated Summary (A)** is shown in a blue highlighted box.
3. **Task 1** — Sentiment guess (slider 0–10): evaluator guesses what fraction of reviews were positive, based only on reading summary A. Skipped automatically for "Suggestions" subtree nodes.
4. **Reveal** — The actual sentiment distribution is shown after submitting the guess.
5. **Source material** is shown — raw review tuples for leaf nodes (grouped by sentiment: positive / negative / suggestion), or child sub-topic summaries for internal nodes.
6. **Task 2** — Quality ratings for summary A (Faithfulness, Coverage, Coherence, each 1–5).
7. **Task 3** — Section alignment check: does the "Appraisals" section of A match summary B? Does the "Criticisms" section of A match summary C?
8. **Task 4** — Propagation check: do the key points of this node's summary appear in the parent node's summary?
9. Optional free-text comments, then Submit.

## 2. Running a New Evaluation (Different Dataset or Model)

### Step 1 — Start the vLLM server

```bash
conda run -n jaleel_btp python run_vllm.py --model <model-name>
# e.g. --model Qwen/Qwen2.5-3B-Instruct
# Wait until the server prints "Application startup complete"
```

### Step 2 — Run the summarisation pipeline

```bash
conda run -n jaleel_btp python run_pipeline.py \
    --dataset acad-real \          # or acad-syn
    --model Qwen/Qwen2.5-3B-Instruct \
    --host http://localhost:8000/v1
```

`--skip-split` can be added if the dataset was already split in a previous run (splits in `data/` are shared across models).

Outputs are written to `outputs/<dataset>/<model-slug>/course_N/`:
- `leaf_summaries.json`
- `internal_summaries.json`
- `course_summary.json`
- `human_eval/course_N_eval.json`
- `human_eval/all_eval.json`

### Step 3 — Update the eval app config

Open `eval_app/config.py` and change the two top variables:

```python
DATASET   = "acad-real"            # or "acad-syn"
MODEL_SLUG = "Qwen2-5-3B-Instruct" # must match directory name under outputs/
```

The `MODEL_SLUG` must exactly match the directory name that the pipeline created under `outputs/<dataset>/`. Check with:

```bash
ls outputs/acad-real/
```

### Step 4 — (Re-)generate eval packages if needed

If you changed the sample selection logic (e.g., `MAX_LEAF_TUPLES` in `src/human_eval.py`) without re-running the full LLM pipeline:

```bash
conda run -n jaleel_btp python regenerate_eval.py \
    --dataset acad-real \
    --model Qwen2-5-3B-Instruct
```

This rebuilds `all_eval.json` from the already-saved summaries without re-calling the LLM.

### Step 5 — Start the evaluation app

From the project root, in a tmux session (so it keeps running after you disconnect):

```bash
tmux new -s eval_app
conda run -n jaleel_btp streamlit run eval_app/app.py
# Ctrl+B then D to detach
```

Responses are saved to `eval_results/responses_<dataset>_<model>.csv` and `eval_results/registry_<dataset>_<model>.json`.

### Step 6 — Generate the report

Once evaluators have submitted responses:

```bash
conda run -n jaleel_btp python eval_app/compute_report.py
# or for a specific model:
conda run -n jaleel_btp python eval_app/compute_report.py --model Qwen2-5-3B-Instruct
```

Outputs are written to `eval_results/report/`.

## 3. Interpreting the Report

### Sentiment Distribution (by node level)

Shows the breakdown of positive / negative / suggestion review tuples across all evaluated nodes, broken down by taxonomy level and by leaf vs. internal. This is descriptive — it tells you what kind of feedback the dataset contains, and whether the signal is balanced or skewed.

### Task 1 — Sentiment Prediction Accuracy

**What it measures:** Whether the consolidated summary (A) accurately conveys the overall sentiment balance of the underlying reviews. Evaluators read summary A and guess on a 0–10 scale how positive the feedback is, before seeing the source reviews. The actual score is computed as `round(positive_tuples / total_tuples × 10)`.

**Key metrics:**

| Metric | Interpretation |
|--------|---------------|
| **MAE (0–10)** | Mean absolute error between guess and actual. Lower is better. A MAE of 0–1 is excellent; 2–3 is acceptable; above 3 means the summary is misleading about sentiment. |
| **Bias** | Positive bias means evaluators (or the summary) over-estimates positivity; negative means under-estimation. |
| **Pearson r** | Correlation between guesses and actuals. Higher means the summary reliably conveys relative sentiment even if absolute values are off. |

**Scatter plot** (`task1_scatter.png`): points close to the diagonal dashed line indicate accurate sentiment signalling.

### Task 2 — Summary Quality Ratings (1–5)

Three dimensions rated per summary:

| Dimension | What it asks | What a low score means |
|-----------|-------------|----------------------|
| **Faithfulness** | Does the summary contain only information present in the source? | The model is hallucinating or inventing claims not in the reviews. |
| **Coverage** | Does it capture all important points from the source? | The model is missing key themes — evaluators found significant gaps. |
| **Coherence** | Is the summary well-written and easy to read? | The summary is poorly structured, repetitive, or hard to follow. |

Results are broken down by **node level** (leaf vs. internal, and level within the tree) and by **node type**. Typically, leaf-level summaries should be more faithful (direct input), while internal summaries may degrade in faithfulness as they aggregate across child summaries.

**Inter-annotator agreement (IAA)** is computed as Krippendorff's α (ordinal) on the 3 core records that all evaluators rated. Interpretation:

| α value | Agreement level |
|---------|----------------|
| < 0.2 | Poor — evaluators interpret the scale very differently |
| 0.2 – 0.4 | Fair |
| 0.4 – 0.6 | Moderate |
| 0.6 – 0.8 | Substantial |
| > 0.8 | Near-perfect |

### Task 3 — Consolidation Alignment

**What it measures:** Whether the "Appraisals" section of the consolidated summary (A) and the standalone positive summary (B) convey the same key points, and similarly for "Criticisms" (A) vs. the standalone negative summary (C).

This tests whether the model's consolidated summary is internally consistent with its own focused summaries.

**How to read it:**

| Response | Meaning |
|----------|---------|
| Yes, fully | Perfect alignment — the consolidated section and focused summary say the same things |
| Mostly | Minor omissions or phrasing differences, but substantively the same |
| Partially | Noticeable divergence — one covers points the other misses |
| No | Significant mismatch — the two summaries tell meaningfully different stories |

**Agreement rate** (Yes + Mostly) is reported as a percentage. A rate above 80% indicates the model's different summary types are mutually consistent.

### Task 4 — Propagation Faithfulness (1–5)

**What it measures:** Whether key points from a child node's summary appear in its parent node's summary. This tests whether information is faithfully preserved as summaries are aggregated up the taxonomy tree.

**Scale:**

| Score | Meaning |
|-------|---------|
| 5 | All key points from the child summary clearly appear in the parent |
| 3–4 | Most key points present; minor losses |
| 2 | Only some key points preserved |
| 1 | Child summary's content is largely absent from the parent |

Results are broken down by **source node level**. Propagation loss at lower levels (closer to root) is expected since the root combines many children. If leaf-to-L1 propagation scores are already low, it suggests the internal summarisation prompts need improvement.

## 4. Sharing the App with External Evaluators

The Streamlit app binds to three addresses when it starts:

```
Local URL:    http://localhost:8501       ← only accessible on the server itself
Network URL:  http://192.168.x.x:8501    ← accessible on the same Wi-Fi / LAN
External URL: http://<public-ip>:8501    ← accessible from anywhere on the internet
```

### For evaluators on the same network (LAN/Wi-Fi)
Share the **Network URL** (`192.168.x.x:8501`). No extra setup needed.

### For evaluators outside your network (recommended: ngrok)

The External IP listed by Streamlit **may not work** unless port 8501 is explicitly opened in the server's firewall and your router's port-forwarding rules — which typically requires admin access.

The reliable alternative is **ngrok**, which creates a secure public tunnel without needing any firewall changes:

```bash
# Install once
pip install pyngrok   # or download from ngrok.com

# In a separate tmux pane, while Streamlit is running:
ngrok http 8501
```

ngrok prints a public URL like `https://abc123.ngrok.io`. Share that URL with all evaluators — it works from any device, anywhere. The free tier supports the load of a small evaluation study (8–10 evaluators).

> **Note:** Keep the tmux session with Streamlit running and the tmux session with ngrok running at all times. If either is killed, the URL stops working. Responses already submitted are saved to disk and are not lost.
